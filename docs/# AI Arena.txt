# AI Arena

## Product Requirements Document

**Status:** Concept / Pre-Development
**Working Name:** AI Arena
**Initial Prototype Foundation:** Terminal Bridge v2.0
**Primary Objective:** Build a neutral environment where multiple AI systems can communicate, disagree, collaborate, test ideas, use shared tools under human-controlled permissions, and iteratively converge toward stronger solutions without requiring a human to manually relay messages between them.

---

# 1. Executive Summary

AI Arena is a multi-agent collaboration environment designed to place independent AI systems into the same shared problem-solving space.

The system is intended to support participants including:

* Multiple ChatGPT instances
* OpenAI/API-based agents
* Claude
* Gemini
* Grok
* Local models
* Future frontier or specialized models

The Arena is not intended to determine which model is the "winner."

Its purpose is to allow multiple reasoning systems to:

* propose ideas
* challenge assumptions
* identify risks
* revise solutions
* request evidence
* run experiments
* use tools
* reconsider earlier conclusions
* preserve unresolved disagreements
* converge when sufficient agreement has been reached

The central product insight is:

> **Build the room, not the participant.**

Models will change over time. Providers will change. Capabilities will improve. The Arena should remain the stable orchestration, communication, state, permission, and collaboration layer in which those systems interact.

The long-term experience should resemble several intelligent participants sitting around the same table, reasoning together in real time while a human retains ultimate authority over the environment and its capabilities.

---

# 2. Background

The project originated from a manually orchestrated workflow involving multiple AI systems.

The user acted as an intermediary between ChatGPT and another AI development environment by manually copying and pasting messages between them.

The practical flow was:

```text
ChatGPT
    ↓
Human copy/paste
    ↓
Development AI
    ↓
Human copy/paste
    ↓
ChatGPT
```

Despite being manual, this demonstrated several important properties:

* distinct AI systems can productively collaborate
* one system can reason while another implements
* different systems identify different problems
* disagreements can improve the resulting solution
* the human intermediary was effectively performing routing and orchestration

The goal is to remove the human from low-value transport work while preserving human authority.

The desired evolution is:

```text
AI Participant
      ↕
Arena Core
      ↕
AI Participant
```

with the human controlling the Arena rather than manually carrying messages between participants.

# 3. Existing Technical Foundation

The first foundational component has already been implemented: **Terminal Bridge v2.0**.

The Terminal Bridge provides a local-first interface exposing terminal and system information to AI-capable clients.

Its default mode is intentionally read-only, binds to localhost, and makes no outbound network connections. Control functionality must be explicitly enabled.

The bridge already provides:

* terminal event capture
* managed PowerShell/CMD sessions
* process information
* filesystem inspection
* bounded file reads
* filesystem tree inspection
* unified system/context snapshots
* HTTP API access
* MCP access
* Server-Sent Events for terminal telemetry
* optional authenticated shell control

The MCP tool layer exposes:

* `get_context_snapshot`
* `get_events`
* `read_file`
* `list_directory`

and conditionally exposes:

* `execute_command`

when control mode is enabled.

Command execution requires both control mode and authorization.

The bridge therefore establishes an important architectural precedent:

> **Observation and execution authority are separate capabilities.**

That principle should carry directly into AI Arena.

# 4. Product Vision

AI Arena should allow a user to create a room, provide a topic or objective, select participating AI systems, and allow those systems to communicate directly with one another without requiring manual relay.

Example:

```text
               HUMAN
                 │
          intent / authority
                 │
                 ▼
         ┌────────────────┐
         │   Arena Core   │
         └───────┬────────┘
                 │
     ┌───────────┼────────────┐
     │           │            │
    GPT       Claude       Gemini
     │           │            │
     └───────────┼────────────┘
                 │
        Capability Broker
                 │
     ┌───────────┼────────────┐
     │           │            │
 Terminal     Browser      Files
```

The Arena should allow model differences to remain visible.

It should not artificially homogenize participants with forced personas unless explicitly requested by the user.

The baseline Arena prompt should primarily define:

* topic
* objective
* constraints
* discussion rules
* available capabilities
* stopping conditions

The natural interaction characteristics of each model or account should remain intact.

# 5. Product Philosophy

## 5.1 Convergence, Not Competition

The system should not be designed primarily around declaring a winning AI.

Instead, participants should iteratively improve a solution until:

* objections have been addressed
* important evidence has been considered
* known failure modes have been surfaced
* tradeoffs are understood
* remaining uncertainty is documented

A final result may contain full agreement or explicit disagreement.

The Arena should never force artificial consensus.

---

## 5.2 Disagreement Is Productive

Disagreement should be treated as a first-class system state.

A disagreement can trigger:

* clarification
* revision
* research
* testing
* benchmarking
* simulation
* tool use
* independent analysis

Example:

```text
Agent A:
"This architecture should scale."

Agent B:
"I disagree."

Arena:
"What evidence would resolve the disagreement?"

Participants:
"Benchmark 50,000 concurrent connections."

Arena:
→ request permission
→ execute benchmark
→ return results
→ continue discussion
```

The ideal loop is:

```text
DISAGREEMENT
     ↓
Required evidence identified
     ↓
Research / experiment / test
     ↓
Evidence returned
     ↓
Participants reconsider
     ↓
Revision or convergence
```

---

## 5.3 Human Authority

The human operator remains the highest authority in the system.

The user should be able to:

```text
/mute
/freeze
/resume
/stop
/ask
/broadcast
/private
/grant
/revoke
/branch
/merge
/summarize
```

The human should not need to manually relay normal conversation.

Human involvement should instead focus on:

* setting objectives
* granting authority
* resolving policy boundaries
* directing discussion
* judging when desired
* interrupting when necessary

# 8. Participant Identity

Every participant must possess a durable Arena identity.

Example:

```json
{
  "participant_id": "gpt-a",
  "provider": "openai",
  "session_role": "participant",
  "capabilities": []
}
```

Identity must remain independent from model/provider implementation.

The Arena should support multiple instances of the same provider or even the same model.

Example:

```text
GPT-A
GPT-B
Claude-A
Gemini-A
Local-Qwen
```

# 9. Model Personality Preservation

The Arena should avoid overwriting natural participant behavior by default.

Participants should not automatically receive prompts such as:

```text
"You are the skeptic."
"You are the funny one."
"You are the technical one."
```

unless explicitly configured.

The default experiment should preserve:

* account-level behavioral differences
* provider/model differences
* context differences
* conversation-history differences
* naturally occurring tone differences

This enables longitudinal observation of participant behavior.

Potential observable behavioral traits include:

```text
challenge frequency
concession behavior
novel idea generation
implementation focus
risk detection
repetition
confidence
reframing
conversation repair
humor
synthesis ability
```

These should be treated as observations rather than forced personas.

# 10. Core System Architecture

## 10.1 Arena Core

The Arena Core is the authoritative orchestration layer.

Responsibilities include:

* session management

* message routing
* turn ownership
* event ordering
* conversation branching
* queue management
* context management
* capability requests
* permission enforcement

# 11. Model Adapter Layer

Every provider should communicate through an adapter.

Examples:

```text
OpenAI Adapter
Claude Adapter
Gemini Adapter
Grok Adapter

```

Adapters normalize provider differences into one Arena protocol.

The Arena should not depend directly on provider-specific message formats.

Each adapter should translate:

```text
Arena message
      ↓
Provider request
      ↓
Provider stream
      ↓
Arena events
```



# 13. Message Ordering

Message ordering must be deterministic.

Every Arena event should receive a monotonically increasing sequence number.

Example:

```text
arena_seq: 100
arena_seq: 101
arena_seq: 102
```

This ensures that the Arena can reconstruct:

* what happened
* in what order
* what information each participant had received
* what caused a particular response

A debugging requirement should eventually allow answering:

> Exactly what information had Participant B received before producing Message 493?

---

# 14. Streaming Protocol

Streaming behavior is a critical product requirement.

The user specifically wants conversation to feel continuous rather than:

```text
Agent A stops
↓
long pause
↓
Agent B begins processing
↓
long pause
↓
response
```

The desired experience is closer to:

```text
Agent A is speaking
↓
Agent B is already ingesting the stream
↓
Agent A completes the turn
↓
Agent B finalizes
↓
Agent B immediately receives the floor
```

However, participant B must not commit an official response before participant A's authoritative turn has ended.

The system should therefore distinguish:

```text
speculative ingest
↓
finalization barrier
↓
response commit
```

---

# 15. Turn Lifecycle

The Arena protocol should include explicit turn-state events.

Example:

```text
START_TURN
TOKEN_CHUNK
TOKEN_CHUNK
TOKEN_CHUNK
END_MESSAGE
END_TURN
```

Then:

```text
ACK_TURN
START_TURN
```

`END_MESSAGE` and `END_TURN` should remain distinct.

This allows future flows such as:

```text
message
↓
tool request
↓
tool result
↓
follow-up
↓
END_TURN
```

```text

```

These should reflect adapter/provider state rather than falsely claiming access to hidden model cognition.

---

# 17. Floor Control

Only the Arena controls the public floor.

A participant should not directly interrupt another participant's output stream.

Instead:

```json
{
  "type": "floor_request",
  "reason": "The previous claim appears factually incorrect.",
  "priority": "challenge"
}
```

The scheduler determines who speaks next.

This prevents participants from drowning each other out while preserving spontaneous interaction.

---

# 18. Per-Participant Inbound Queues

Each participant should receive a separate inbound message queue.

Example:

```text
GPT inbox
Claude inbox
Gemini inbox
Grok inbox
Local inbox
```

The system must never assume all participants consume messages at the same rate.

---

# 19. Backpressure

The Arena must support backpressure.

If a participant falls behind:

```text
queue grows
↓
Arena detects lag
↓
new turn scheduling pauses or adapts
↓
context is checkpointed / summarized if necessary
↓
participant catches up
↓
session resumes
```

Messages must never be silently discarded.

---

# 20. Reliability Requirements

The Arena should follow several strict invariants.

## Required Invariants

* Every message has an ID.
* Every event has a sequence number.
* Every turn has an owner.
* Every stream has an explicit end condition.
* No message is silently dropped.
* No participant can overwrite another participant's stream.
* Interruptions are requested through the Arena.
* Tool requests are auditable.
* Retries should be idempotent.
* Message order must be reconstructable.
* State transitions must be explicit.
* Participant failures must not corrupt the session.
* Final responses must not precede their causal inputs.

# 22. Consensus Protocol

The Arena should support explicit participant stances.

Possible states:

```text
SUPPORT
SUPPORT_WITH_RESERVATION
OBJECT
NEEDS_EVIDENCE
PROPOSE_REVISION
BLOCKING_ISSUE
```

A proposal should continue through discussion until:

* objections are addressed
* evidence is collected
* revisions stabilize
* participants support the proposal

or:

* unresolved disagreement remains

---

# 23. Consensus Definition

Consensus should not simply mean that all participants said "yes."

Consensus means participants believe:

* the stated objective is satisfied
* no known blocking issue remains
* major tradeoffs are understood
* remaining uncertainty is documented

Possible outcome:

```text
CONSENSUS: YES

RESERVATIONS:
Claude:
Failure mode X remains possible and should be monitored.
```

---

# 24. Minority Reports

Participants must be able to preserve reservations after consensus.

This reduces groupthink.

Example:

```text
Consensus:
Adopt architecture B.

Minority reservation:
Participant C believes architecture B may create scaling pressure beyond 10M events/day.
```

---

# 25. Loop Prevention

The Arena must detect unproductive reasoning loops.

Potential signals include:

```text
same recommendation repeated multiple times
same objection repeated without new evidence
multiple failed implementations
high confidence with no new evidence
participants paraphrasing one another
no change in shared state
```

When detected, the Arena may:

* request independent analysis
* ask another participant
* request evidence
* run a test
* summarize the disagreement
* ask the human
* terminate the branch

---

# 26. Deadlock Escalation

Current manual usage has demonstrated the value of switching to a different AI instance when one conversation becomes stuck.

The Arena should automate this pattern.

Example:

```text
STALLED

Requesting independent analysis from Participant C.
```

A fresh participant may identify assumptions missed by the existing participants.

---

# 27. Conversation Branching

Future versions should support side discussions.

Example:

```text
Main Room
   │
   ├── Branch 17
   │     GPT ↔ Claude
   │     architecture disagreement
   │
   ├── Branch 18
   │     Gemini ↔ Local
   │     benchmark investigation
   │
   └── Results merged into main room
```

Branches allow parallel reasoning while preventing the main conversation from becoming unreadable.

# 32. Security Model

Security should be designed around explicit authority boundaries.

Principles:

* read access does not imply write access
* tool availability does not imply tool permission
* participant identity must be authenticated internally
* dangerous actions should require appropriate scope
* permissions must be revocable
* actions must be logged
* secrets should be protected
* tool access should default toward minimum required scope

The current Terminal Bridge already blocks several obvious credential file patterns during AI file inspection.


# 46. Performance Goals

Long-term conversational responsiveness should minimize dead time between participants.

Desired flow:

```text
Speaker A streaming
↓
Speaker B receives incremental content
↓
Speaker B performs speculative ingest
↓
Speaker A reaches END_TURN
↓
finalization barrier
↓
Speaker B commits response
↓
immediate handoff
```

The goal is to create the perception of a live conversation without violating causal message ordering.

---

Large Arena sessions will eventually exceed model context limits.

Future requirements include:

* transcript segmentation
* canonical shared-state summaries
* per-branch summaries
* participant-specific context
* recent-message windows
* durable artifacts
* evidence indexes
* important-decision preservation

Summarization must not silently erase unresolved objections.

# 48. Failure Handling

The Arena should expect:

* API failures
* provider outages
* rate limits
* malformed responses
* stream disconnects
* duplicate events
* participant timeouts
* context overflow
* tool failures

Failures must be explicit Arena events.

No failure should silently disappear.

# 49. Provider Independence

Arena Core must not depend heavily on any single model provider.

The architecture should assume:

```text
models change
APIs change
pricing changes
context limits change
providers disappear
new providers appear
```

Adapters should absorb provider-specific behavior.

The Arena remains stable.

---

# 50. Key Product Differentiator

Most multi-model interfaces effectively do:

```text
prompt
↓
Model A answer
Model B answer
Model C answer
↓
human compares
```

AI Arena should instead do:

```text
problem
↓
participants reason
↓
participants challenge
↓
participants revise
↓
participants request evidence
↓
tools / research / experiments
↓
participants reconsider
↓
solution evolves
```

The difference is **interaction between models**, not merely parallel generation.

# 51. Long-Term Product Identity

AI Arena should ultimately be understood as:

> **A multi-agent operating environment for collaborative reasoning and tool use.**

It is not merely:

* a chatbot frontend
* a model benchmark
* a debate website
* an API aggregator
* a coding assistant

Those may all be capabilities of the system.

The larger abstraction is the shared environment itself.

# 52. Core Product Principles

1. **The Arena is neutral.**
2. **Human authority remains supreme.**
3. **Models remain distinct participants.**
4. **Natural behavioral differences should be preserved.**
5. **Disagreement is useful information.**
6. **Consensus must be earned, not forced.**
7. **Evidence should resolve disagreements when possible.**
8. **Tools belong to the Arena, not individual models.**
9. **Permissions must be explicit and revocable.**
10. **No message should silently disappear.**
11. **Everything important should be reconstructable.**
12. **Streaming must preserve causal ordering.**
13. **The initial system should remain simple enough to debug.**
14. **Complexity should be added only after the underlying protocol is trustworthy.**

The Arena should remain in design state until current deployment work on the user's existing projects is completed.

When implementation begins, the first development objective should be:

> **Automatically route a real conversation between two ChatGPT instances with deterministic message sequencing and no human copy/paste.**

# 55. Transport & Wire Architecture

## 55.1 Protocol Binding Options
The Arena Core communicates with Model Adapters, Tool Brokers, Human Interfaces, and External Bridges across two primary transport topologies:

1. **WebSocket Full-Duplex Transport (Primary - RFC 6455):**
   - Base endpoint: `ws://127.0.0.1:8765/v1/arena/stream`
   - Subprotocol: `arena.v1.jsonrpc`
   - Message Framing: JSON-RPC 2.0 frames encapsulated in UTF-8 text frames.
   - Purpose: Low-latency streaming of token chunks, bidirectional backpressure notifications, interactive floor arbitration, and sub-millisecond turn handoffs.

2. **HTTP/SSE Transport (Secondary / Ingestion-Only):**
   - Ingestion endpoint: `POST http://127.0.0.1:8765/v1/arena/events`
   - Telemetry downlink: `GET http://127.0.0.1:8765/v1/arena/telemetry` (Content-Type: `text/event-stream`)
   - Purpose: Passive loggers, human observation dashboards, headless replay workers, and environments where persistent full-duplex WebSockets cannot be maintained.

## 55.2 Connection Handshake & Authentication
Every incoming adapter or controller connection must authenticate within `5000ms` of socket establishment.

# 57. Deterministic Event Sequencing & Replay Log

## 57.1 Sequence Ordering Rules
1. **Strict Monotonicity:** Every event committed by Arena Core receives `arena_seq = previous_arena_seq + 1`. Gaps are strictly prohibited.
2. **Causal Prior Assertions:** Every event declares `causal_prior_seq`. The Arena ingestion engine verifies:
   $$\text{causal\_prior\_seq} \le \text{arena\_seq} - 1$$
   If an adapter attempts to commit an event asserting a causal baseline it has not yet ingested, the transaction is rejected with `ERR_CAUSAL_VIOLATION`.
3. **Branch Identifiers:** Sequences remain continuous across branches. A branch event increments `arena_seq` while recording `parent_branch_id` and `branch_point_seq`.

## 57.2 Storage Engine & In-Memory Append Log
- **Append-Only Write Ahead Log (WAL):**
  Events are flushed synchronously to disk using newline-delimited JSON (`.jsonl`) with immediate file-descriptor `flush()` and periodic OS page sync (`fsync` every 100ms or on critical lifecycle boundaries).
- **In-Memory Ring Buffer:**
  Maintains the most recent 10,000 events in a fixed-size contiguous array for zero-copy streaming to WebSocket consumers and reconnection resynchronization.

## 57.3 Replay Engine Interface
```python
class ArenaReplayEngine:
    def replay_session(self, session_id: str, up_to_seq: int | None = None) -> Iterator[ArenaEvent]:
        """Reads WAL deterministically, validating hash-chain integrity."""
        ...

    def get_state_at_seq(self, session_id: str, target_seq: int) -> ArenaSessionState:
        """Reconstructs exact Blackboard, Participant stances, and floor status at seq."""
```

# 59. Streaming Protocol & Speculative Concurrency

## 59.1 The Speculative Pipeline
To eliminate turn-to-turn latency ("dead air") while maintaining deterministic causality, non-speaking participants run speculative pre-processing:

```text
Speaker (GPT-A)                   Arena Core                     Listener (Claude-B)
      │                               │                                  │
      ├─── turn.chunk (1..20) ───────►│                                  │
      │                               ├─── speculative.chunk ───────────►│ (Ingesting into
      ├─── turn.chunk (21..40) ──────►│                                  │  scratch buffer)
      │                               ├─── speculative.chunk ───────────►│
      ├─── turn.end_message ─────────►│                                  │
      │                               ├─── BARRIER_SEAL ────────────────►│ (Begin draft reasoning;
      ├─── turn.end ─────────────────►│                                  │  NO COMMIT ALLOWED)
      │                               ├─── FINAL_COMMIT_PERMIT ─────────►│ (Verify match)
      │                               │                                  ├─ Discard if drift
      │                               │                                  └─ Commit & speak
```

## 59.2 Speculative Guardrails
1. **Speculation Tagging:** All chunks forwarded prior to `turn.end` are marked `is_speculative: true`.
2. **Zero Emission Guarantee:** A participant in speculative ingest MUST NOT emit any external events or request capabilities.
3. **Invalidation Criterion:** If the speaker aborts, errors, or modifies the turn via tool results before conclusion, the Arena Core issues `speculative.abort { turn_id: X }`. The listener must immediately discard the speculative drafting context.
4. **Finalization Barrier:** The Arena holds the floor lock until `turn.end` and `turn.ack` have completed. Only then is `FINAL_COMMIT_PERMIT` dispatched.

# 60. Floor Control & Scheduling Engine

## 60.1 Scheduling Modes
1. **Round-Robin (Deterministic Order):**
   Fixed rotation: `Agent A` $\rightarrow$ `Agent B` $\rightarrow$ `Agent C` $\rightarrow$ `Agent A`.
2. **Priority-Arbitrated (Deliberation Default):**
   Participants request the floor with priority tags. Scheduler evaluates weights every turn boundary.
3. **Moderated / Human Directed:**
   Human manually picks the next speaker or injects prompts.
4. **Chaos Mode (Advanced):**
   Cooperative interrupts with sub-turn floor snatching (governed by §60.3).

## 60.2 Priority Ranking Formula
When multiple participants submit `floor.request`, the scheduling score $S$ is calculated:

$$S = W_{\text{category}} + (\alpha \cdot T_{\text{wait}}) - (\beta \cdot T_{\text{recent\_turns}}) + \gamma_{\text{direct\_address}}$$

Where:
- $W_{\text{category}}$:
  - `BLOCKING_VULNERABILITY`: 100
  - `FACTUAL_CORRECTION`: 75
  - `EVIDENCE_SUBMISSION`: 60
  - `REVISION_PROPOSAL`: 40
  - `GENERAL_ARGUMENT`: 20
- $T_{\text{wait}}$: Milliseconds elapsed in queue ($\alpha = 0.01$).
- $T_{\text{recent\_turns}}$: Number of turns taken in the last 10 turns ($\beta = 15$). Prevents single-model dominance.
- $\gamma_{\text{direct\_address}}$: Bonus (+50) if the prior speaker explicitly addressed this participant.

## 60.3 Interruption Protocol
- An agent wishing to interrupt sends `floor.request { priority: "INTERRUPT" }`.
- Interruption is granted ONLY if:
  - Enabled by Session Policy (`allow_interrupts: true`).
  - Requester priority exceeds speaker's active priority by at least 40 points.
  - Active speaker has completed at least 150 tokens (preventing micro-stutters).
- If granted, Arena dispatches `turn.interrupt` to active speaker. Speaker must emit `turn.end { reason: "interrupted" }` within 500ms or be forcefully cut.

# 61. Per-Participant Queues & Backpressure System

## 61.1 Inbound Mailbox Topology
- Every connected participant maintains a dedicated, isolated FIFO queue on the Arena server.
- Events destined for the participant are pushed to its mailbox with monotonically increasing `delivery_seq`.

```text
                      ┌──────────────────────┐
                      │    Arena Event Bus   │
                      └──────────┬───────────┘
                                 │
         ┌───────────────────────┼───────────────────────┐
         ▼                       ▼                       ▼
  ┌─────────────┐         ┌─────────────┐         ┌─────────────┐
  │ GPT Inbox   │         │Claude Inbox │         │ Local Inbox │
  │ [q_len: 2]  │         │ [q_len: 0]  │         │[q_len: 480] │
  └─────────────┘         └─────────────┘         └──────┬──────┘
                                                         │ HIGH WATERMARK!
                                                         ▼
                                                  Arena Flow Control
                                                  (Suspend Floor Scheduler)
```

## 61.2 Watermark Semantics & Mitigation
- **Capacity Limits:** Default queue capacity = 500 events.
- **High Watermark (80% / 400 events):**
  - Arena sends `flow.pause` to fast generators.
  - Scheduler delays granting new turns.
  - Telemetry alerts operator: `WARN: Participant 'local-qwen' lagging behind (depth: 412)`.
- **Low Watermark (20% / 100 events):**
  - Once consumer drains below 100 events, Arena sends `flow.resume`.
- **Overflow Prevention (Zero Drop Guarantee):**
  - Arena **never** drops deliberation messages.
  - If a queue reaches 100%, the entire session execution halts in `SESSION_THROTTLED` state until the slow consumer digests messages or operator evicts the lagging participant.

# 63. Consensus Protocol & Dissent Registry

## 63.1 Stance Taxonomy
Every participant must register one of six formal stances on active proposals:
1. `SUPPORT`: Total agreement with all terms and assumptions.
2. `SUPPORT_WITH_RESERVATION`: Agrees to proceed, but registers an explicit risk to be tracked.
3. `OBJECT`: Disagrees based on substantive counter-arguments; proposes alternative or demands change.
4. `NEEDS_EVIDENCE`: Position withheld pending experimental data or external verification.
5. `PROPOSE_REVISION`: Agrees with goal, but offers a specific textual amendment.
6. `BLOCKING_ISSUE`: Hard architectural/security veto. Halts proposal progression until resolved.

## 63.2 Consensus Evaluation Algorithm
```text
FUNCTION EvaluateConsensus(proposal):
    LET stances = GetActiveParticipantStances(proposal.id)
    
    IF Count(stances) < TotalActiveParticipants():
        RETURN ConsensusResult(STATUS="INCOMPLETE", CAN_CONVERGE=FALSE)
        
    IF Any(s.type == "BLOCKING_ISSUE" FOR s IN stances):
        RETURN ConsensusResult(STATUS="VETOED", CAN_CONVERGE=FALSE)
        
    IF Any(s.type == "NEEDS_EVIDENCE" FOR s IN stances):
        RETURN ConsensusResult(STATUS="PENDING_EVIDENCE", CAN_CONVERGE=FALSE)
        
    IF Any(s.type == "OBJECT" FOR s IN stances):
        RETURN ConsensusResult(STATUS="DISPUTED", CAN_CONVERGE=FALSE)
        
    # All are SUPPORT or SUPPORT_WITH_RESERVATION
    LET reservations = [s FOR s IN stances IF s.type == "SUPPORT_WITH_RESERVATION"]
    RegisterMinorityReport(proposal.id, reservations)
    
    RETURN ConsensusResult(STATUS="CONVERGED", CAN_CONVERGE=TRUE, RESERVATIONS=reservations)
```

## 63.3 Minority Report Archival
Consensus **does not** overwrite reservations. Upon convergence, all recorded reservations are permanently serialized into the room’s `CONVERGENCE_REPORT.md` artifact under the `Minority Reservations` section.

# 64. Loop Detection & Anti-Stagnation Engine

## 64.1 Detection Metrics
The Loop Detector evaluates the deliberation log over a rolling window of $K=6$ turns using three algorithms:

1. **Exact & Near-Deduplication (Cosine Similarity over Embeddings / MinHash):**
   If similarity between participant $P_i$'s turn $T_n$ and prior turn $T_{n-2}$ exceeds 0.88 with no new evidence introduced, a duplicate argument flag is raised.
2. **Ping-Pong Rebuttal Detection:**
   Identifies cyclic 2-party dialogues where stances oscillate without changes to the Blackboard state:
   $$\text{Stance}(A) \leftrightarrow \text{Stance}(B) \quad \text{for } \ge 3 \text{ cycles}$$
3. **No-Progress Threshold:**
   If 8 consecutive turns yield 0 Blackboard patches and 0 capability requests, stagnation is triggered.

## 64.2 Escalation Matrix
| Trigger Level | Signal | Action Executed by Arena Core |
|---|---|---|
| **Level 1 (Warning)** | Repetition detected once | Inject system prompt: *"Arena Notice: Claim X has been stated without new data. What specific test will resolve this?"* |
| **Level 2 (Intervention)** | Cyclic ping-pong detected | Temporarily silence both participants; grant floor to a third independent participant (e.g. `Gemini` or `Local`). |
| **Level 3 (Evidence Mandate)** | Deadlock on empirical claim | Arena scheduler forces a tool execution turn or requires participants to frame a testable benchmark. |
| **Level 4 (Human Escalation)** | Unresolved deadlock > 10 turns | Arena executes `session.pause` and signals operator with a structured disagreement summary. |

## 65.2 Capability Lease Lifecycle
1. **Request:** Model emits `capability.request { capability_id: "terminal.execute", command: "..." }`.
2. **Authorization:** Broker verifies:
   - Is `terminal.execute` enabled in the session policy?
   - Does participant have execution clearance?
   - If requiring human clearance, prompt operator via UI/CLI.
3. **Lease Issuance:** Broker mints an ephemeral HMAC lease token valid for $T \le 300\text{ seconds}$.
4. **Execution:** Broker calls [terminal_bridge.py](file:///C:/Users/droxa/bridge/terminal_bridge.py) MCP endpoint:
   `POST /mcp` with method `tools/call`, tool `execute_command`, injecting the required bridge authorization header.
5. **Telemetry Telecast:** As stdout/stderr stream from the bridge, the broker broadcasts `capability.chunk` and `capability.result` into the Arena Event stream.

# 66. Human Governance & Interactivity Protocol

## 66.1 Operator Command Grammar
The operator can issue commands at any time via CLI or Webhook. Operator commands preempt all agent turns immediately.

| Command | Arguments | System Effect |
|---|---|---|
| `/freeze` | None | Halts event dispatch immediately. Preserves all socket buffers and timers. |
| `/resume` | None | Restores event loop and active turn clocks. |
| `/stop` | None | Terminates current session, persists complete WAL and Blackboard summary. |
| `/mute` | `<participant_id>` | Revokes speaking authority from model; retains inbound streaming. |
| `/unmute` | `<participant_id>` | Restores model eligibility for floor requests. |
| `/grant` | `<participant_id> <capability> [scope]` | Grants capability lease with optional path or command whitelist. |
| `/revoke` | `<participant_id> <capability>` | Immediately terminates active lease and kills executing subprocesses. |
| `/ask` | `<participant_id> <prompt>` | Directs model to respond next, overriding priority queue. |
| `/broadcast` | `<message>` | Injects human instruction as high-priority system directive to all agents. |
| `/branch` | `<new_branch_id>` | Forks current Blackboard state and conversation tree into isolated side-room. |
| `/merge` | `<branch_id>` | Reconciles accepted assertions from side branch into `main` Blackboard. |
| `/summarize` | None | Prompts all participants to output current consensus and open reservations. |

# 67. Resilience, Fault Tolerance & Disconnect Handling

## 67.1 Failure Modes & Mitigations
1. **Model API Outage / Rate Limit (HTTP 429 / 503):**
   - Adapter catches error and dispatches `system.participant_degraded { participant_id: "X", retry_after_ms: 12000 }`.
   - Arena scheduler marks model `UNAVAILABLE`, retains its inbox queue without eviction, and redistributes turn priority.
2. **Abrupt Socket Disconnection:**
   - On connection drop, participant enters `DISCONNECTED` state.
   - 60-second re-attachment window granted.
   - Upon reconnect, client transmits `arena.resume { last_received_seq: 1042 }`.
   - Arena replays missed events directly from the in-memory ring buffer.
3. **Runaway / Infinite Generation:**
   - Arena Core enforces hard `max_duration_ms` (default 60s) and `max_tokens` (default 2048) per turn.
   - Upon limit breach, Arena issues WebSocket frame `turn.abort` and sends `turn.end { reason: "limit_exceeded" }`.
